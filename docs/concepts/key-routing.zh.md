# Key Routing（核心机制）

---

## 省流版

> Log4Key 按“业务 key”路由日志，而不是按 Logger 名称。

这带来了：

* 按实体隔离日志
* 输出路径确定性
* 无配置膨胀

---

## 什么是 Key Routing？

传统日志模型：

```
logger → appender → 文件
```

Log4Key：

```
log event → key → routing → 文件
```

> **key 成为日志路由的核心维度**

---

## 为什么用 Key，而不是 Logger？

### 传统方式的限制

基于 Logger 的路由依赖：

* 包名
* 类结构

这导致：

* 无法按用户拆分日志
* 无法按订单隔离日志
* 单请求排查困难

---

## Key 路由方式

示例：

```java
logger.info("order created", LogKey.of("order-123"));
```

输出：

```
logs/
├── order-123.log
```

---

## 典型使用场景

### 1. 订单日志

* key = orderId
* 每个订单独立日志

---

### 2. 用户日志

* key = userId
* 快速定位异常用户

---

### 3. 请求链路

* key = requestId
* 一次请求完整日志

---

### 4. 多租户系统

* key = tenantId
* 天然隔离

---

## 核心优势

### 1. 天然分区

无需设计复杂目录结构。

---

### 2. 无配置爆炸

无需：

* 大量 logger 配置
* 动态刷新配置

---

### 3. 确定性输出

一条日志 → 一个 key → 一个文件

---

### 4. 排查效率极高

传统方式：

在海量日志中 grep

现在：

打开一个文件即可

---

## 对比 MDC / ThreadContext

传统做法：

```java
MDC.put("orderId", "123");
```

问题：

* 行为隐式
* 依赖 pattern 配置
* 不是路由核心

---

### Log4Key 方式

* key 是显式参数
* 路由是核心机制
* 无隐式魔法

---

## 性能设计

Key 路由具备：

* O(1) 路由决策
* 极低开销
* 支持高基数 key

---

## 设计理念

> 日志应跟随“业务身份”，而不是“代码结构”。

---

## 总结

Key Routing 让日志从：

* 面向代码 → 面向业务
* 静态 → 动态
* 隐式 → 显式

---

## 最后一句（卖点）

> 只要你能定义 key，就能拥有独立日志。
