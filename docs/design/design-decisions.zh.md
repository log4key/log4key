# 设计取舍说明

---

## 省流版

> Log4Key 是一个基于 key 路由的日志系统，而不是基于层级的日志框架。
> 为了保证确定性与简洁性，它不支持 additivity 和 filter 机制。

---

## 核心差异

传统日志框架：

```
logger → appender → output
```

Log4Key：

```
log event → key → routing → output
```

---

## 为什么不支持 additivity？

### 什么是 additivity？

additivity 表示日志会向父级 logger 传播。

---

### 在 Log4Key 中的问题

#### 1. 破坏确定性

日志可能进入多个不可预测的输出路径。

---

#### 2. 与 key 路由冲突

* additivity 是静态层级传播
* key routing 是动态决策

---

#### 3. 性能成本

* 增加传播开销
* 产生多次写入

---

### 结论

* 不支持 additivity
* 一条日志只进行一次路由决策

---

## 为什么不使用 Filter？

### 什么是 Filter？

Filter 是在日志生成之后进行“是否输出”的判断。

---

### 存在的问题

#### 1. 抽象冗余

路由已经决定输出目标，再增加 Filter 属于重复判断。

---

#### 2. 行为不清晰

示例：

```properties
logger.level = INFO
filter = WARN
```

用户难以判断：

* 日志被过滤了？
* 还是根本没有输出？

---

#### 3. 性能开销

* 每条日志增加额外判断
* 形成链式调用开销

---

## 替代方案：显式级别策略

示例：

```properties
appender.file.level = INFO
appender.file.levelPolicy = AT_LEAST
```

策略说明：

* EXACT：只输出指定级别
* AT_LEAST：输出该级别及以上

---

## 运行时约束

---

### 不支持热更新

Log4Key 不支持运行时配置变更。

所有配置修改均通过进程重启生效，以确保：

* 执行路径的确定性
* 性能特征的稳定性
* 日志顺序的一致性

引入运行时重配置将需要动态路由变更、组件切换以及额外的同步机制，这些都会影响关键执行路径，并引入非确定性行为。

→ 详见：[运行时模型](runtime-model.zh.md)

---

### 确定性执行模型

Log4Key 将线程与队列拓扑视为执行模型的一部分，而非可在运行时调整的参数。

日志事件遵循固定处理路径：

Log Event → Key → Queue → Worker Thread → Output

该模型建立了一个关键保证：

> 相同 Key 的日志始终在一致的执行上下文中按顺序处理。

这一保证依赖于进程生命周期内执行拓扑的稳定性。

如果允许在运行时进行修改，将打破这一前提，并引入无法可靠检测或修复的不一致问题。

因此，执行模型在进程启动后保持固定不变。

→ 详见：[运行时模型](runtime-model.zh.md)

---

## 设计原则

1. 确定性优先于灵活性
2. 简单优先于抽象
3. 性能可预测
4. 降低用户理解成本
