# 运行时模型

---

## 概述

Log4Key 基于确定性执行模型构建。
日志事件从产生到输出遵循固定处理路径，不依赖运行时对路由、线程或队列拓扑的动态修改。

该模型确保：

* 系统行为可预测
* 性能特征稳定
* 基于 Key 的强顺序保证

运行时模型被设计为**静态执行流水线**，而非可动态重配置的系统。

---

## 执行流程

日志事件按照如下流程处理：

Log Event → Key 提取 → 队列路由 → 工作线程 → 输出

各阶段在进程初始化时确定，运行期间不会发生变化。

---

## 基于 Key 的路由

Log4Key 基于用户定义的 Key 进行日志路由：

* 相同 Key 的日志始终进入同一队列
* 从而保证该 Key 内的日志顺序
* 不同 Key 可并行处理

该模型在并发能力与顺序保障之间取得平衡。

---

## 队列模型

队列作为日志接收与处理之间的边界：

特性包括：

* 每个队列绑定一个工作线程
* 队列拓扑在启动时确定
* 提供缓冲与解耦能力

队列行为（如容量、背压策略）通过配置定义，并在运行期间保持稳定。

---

## 线程模型

Log4Key 采用固定工作线程模型：

* 每个工作线程消费一个对应队列
* 线程与队列的映射在运行期间不可变
* 不进行动态扩缩容或重分配

该设计确保：

* 执行路径一致
* 不发生跨线程乱序
* 资源使用可预测

如果在运行时修改线程模型，将改变事件路由并破坏顺序保证。

---

## 确定性执行

确定性是运行时模型的核心特性。

在相同：

* 配置
* 输入日志序列

条件下，Log4Key 将产生一致的：

* 路由结果
* 处理顺序
* 输出内容

这使系统行为更易理解与调试。

---

## 不支持热更新

Log4Key 不支持运行时配置热更新。

所有配置修改均需通过进程重启生效。

该设计避免：

* 路由行为不一致
* 配置部分生效的问题
* 运行时引入的不确定性

热更新会导致执行路径不明确，因此被刻意不支持。

---

## 设计理由

该运行时模型优先考虑稳定性与可预测性，而非灵活性。

Log4Key 不追求动态配置能力，而是确保：

* 执行路径固定
* 系统行为可复现
* 性能特征稳定

这种设计特别适用于日志系统，因为一致性与可靠性比动态适配更重要。
